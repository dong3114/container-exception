## 1. 전체 사용자 흐름

기술 용어보다 **사람이 하는 일** 순서로 적는다. 괄호 안은 이 문서의 요구사항 그룹이다.

### A. 거래처 등록 (FR-CPY)

운영자가 K운송이라는 **거래처**를 만든다 → 그 안에 배차팀 김OO이라는 **담당 연락처**를 만든다 → 그 연락처의 **이메일 주소**를 적는다.
이 시점에서는 아직 아무것도 보낼 수 없다.

### B. 이메일 주소 확인 (FR-EVF)

운영자가 [확인 메일 보내기]를 누른다 → CERA가 그 주소로 확인 메일을 보낸다 → 상대방이 링크를 누른다 → **주소 확인 완료**.
확인의 뜻은 *"그 주소를 열 수 있는 사람이 응답했다"* 뿐이다. 회사를 대표한다는 뜻이 아니다.

### C. 업무 관계 승인 (FR-CPY, FR-ELG)

운영자가 "이 주소를 K운송의 업무 연락처로 쓰겠다"고 **승인**한다 → **통신 활성** 상태가 된다.
이제부터 이 주소로 업무 메시지를 보낼 수 있다.

### D. 문의 생성 (FR-COM)

복구 계획에서 "15~17시 사이 40FT Dry 트럭 3대 부족"이 나온다 → CERA가 K운송에게 보낼 **문의 초안**을 만든다.
**숫자와 조건은 시스템이 넣고**, 필요하면 AI가 **문장만** 쓴다.

### E. 발송 승인 (FR-APV)

운영자가 초안을 읽고 필요하면 고친다 → [승인]을 누른다.
승인 뒤에 내용이 바뀌면 **다시 승인**해야 한다.

### F. 실제 발송 (FR-SND)

CERA가 **받는 사람이 아직 자격이 있는지 다시 확인**한다 → 외부 채널로 보낸다 → 결과를 기록한다.
같은 승인으로 두 번 보내지 않는다.

### G. 회신 수신 (FR-INB)

상대가 답장한다 → CERA가 **원문 그대로 보관**한다 → 보낸 주소로 **어느 거래처의 누구인지 찾는다** → **어느 문의에 대한 답인지 연결**한다.

### H. 내용 해석 (FR-XAI, FR-STC)

- 이미 정리된 형태(응답 폼·포털·연동)로 왔으면 **AI를 쓰지 않는다.**
- 자유롭게 쓴 문장이면 **AI가 값 후보를 뽑는다.** AI는 "무엇을 물었는가 + 값 + 원문 인용"만 돌려준다.

### I. 검증 (FR-XAI, FR-EVL)

서버가 확인한다: 값의 형식·단위가 맞는가 / 보낸 사람이 그 자원에 대해 말할 자격이 있는가 / 물어본 질문에 대한 답인가 / 원문에 실제로 그 근거가 있는가 / 허용된 사실 종류인가.

### J. 운영 정보 반영 (FR-EVL)

검증을 통과한 값이 **사건으로 기록**된다 → 기존 상태 판단 규칙을 거쳐 **현재 상태**가 된다(대개 "잠정") → 필요하면 **사람 확인 요청**이 생긴다.

> **회신 한 통으로 사실이 확정되지 않는다.** 이것이 이 흐름 전체의 안전 근거다.

## 2. 용어 (사람 기준 의미)

구현 형태(테이블 이름·컬럼)는 **정하지 않는다.** 의미만 고정한다.

| 용어 | 뜻 | 예 |
| --- | --- | --- |
| **거래처** | CERA 사용자가 업무상 연락하는 외부 조직 | K운송, ODCY A, 창고 A |
| **담당 연락처** | 그 거래처와의 연락 지점 | 배차팀 김OO, 배차팀 공용 |
| **채널 주소** | 실제로 메시지를 주고받는 주소 | `dispatcher@k-transport.com` |
| **문의 묶음(스레드)** | CERA가 연 하나의 대화. 보낸 것과 받은 것이 여기 묶인다 | "10/13 오후 셔틀 트럭 문의" |
| **문의 메시지** | 묶음 안의 개별 메시지(보낸 것 / 받은 것). 보내는 메시지는 **승인할 내용**(제목·본문·받는 사람·주입된 값)이며 만든 뒤 내용이 바뀌지 않는다 — 바꾸면 새 메시지다 | 초안, 발송본, 회신 |
| **발송 승인** | 사람이 그 메시지의 **그 내용**을 보내도 된다고 한 기록. 내용·받는 사람·값이 바뀌면 다시 승인 | "운영자가 11:02에 승인" |
| **발송 시도** | 메시지 한 통을 실제로 보내려고 외부 채널을 부른 **한 번**. 재시도하면 새 시도가 생긴다. **메시지의 상태(발송 대기·완료·실패)와 같은 것이 아니다** | "1번째 시도 실패(일시 장애), 2번째 성공" |
| **질문 항목** | 한 문의가 묻는 것 하나. 회신의 값이 여기에 연결된다 | "15:00~17:00 40FT Dry 가용 대수" |
| **값 후보** | 아직 사실이 아닌, 검증 대기 중인 값 | "15시 2대" |
| **사건 기록** | 업무 사실에 대한 주장의 원본 기록 (`05`의 Event) | "K운송이 15시 2대 가능하다고 알림" |
| **감사 기록** | 누가 언제 무엇을 했는지의 운영 기록 | "운영자가 11:02에 발송 승인" |

**사건 기록과 감사 기록은 다르다.** 18절 참조.

## 4. 거래처 · 연락처 · 주소 (FR-CPY)

### 4.1 상태 세 가지

채널 주소 하나에 **서로 다른 질문 세 개**의 답이 붙는다. 한 칸에 합치지 않는다.

| 상태 | 묻는 것 | 바꾸는 주체 |
| --- | --- | --- |
| **주소 확인 상태** | 그 주소를 열 수 있는 사람이 응답했나 | 상대방(확인 링크) |
| **업무 관계 상태** | 사용자가 이 주소를 그 거래처의 업무 연락처로 인정했나 | CERA 사용자 |
| **통신 상태** | 지금 이 주소로 보낼 수 있나 | CERA 사용자 또는 정책 |

값 후보: 주소 확인 = `미확인` / `확인 대기` / `확인됨` / `실패` / `만료`. 업무 관계 = `대기` / `승인됨` / `거부됨`. 통신 = `활성` / `일시중지` / `비활성`.
**구현 enum 이름은 정하지 않는다.**

### 4.2 요구사항

| ID | 요구사항 | 우선 |
| --- | --- | --- |
| FR-CPY-01 | 거래처를 만들 수 있다. 최소 정보: 표시 이름, **역할**(운송사·ODCY·창고·선사·터미널), 활성 여부. 역할은 나중에 "이 사람 말을 어디까지 믿을지" 판정의 입력이 되므로 **필수**다 | `[MUST]` |
| FR-CPY-02 | 거래처 정보를 고칠 수 있다. **역할 변경은 과거 사건 기록의 해석을 바꾸지 않는다**(사건은 그때의 역할로 기록된 채 남는다) | `[MUST]` |
| FR-CPY-03 | 거래처를 비활성화할 수 있다. 비활성 거래처의 모든 주소로는 **새 발송이 막힌다.** 이미 열린 문의 묶음의 회신은 계속 받는다 | `[MUST]` |
| FR-CPY-04 | 한 거래처에 담당 연락처를 여럿 만들 수 있다. 최소 정보: 표시 이름(사람 이름 또는 팀 이름), 소속·비고, 활성 여부 | `[MUST]` |
| FR-CPY-05 | 담당 연락처를 고치거나 비활성화할 수 있다. 비활성 연락처의 주소로는 새 발송이 막힌다 | `[MUST]` |
| FR-CPY-06 | 한 담당 연락처에 채널 주소를 여럿 등록할 수 있다(예: 업무용·백업용). 주소는 **정규화**해서 저장한다(대소문자·공백) | `[MUST]` |
| FR-CPY-07 | 같은 주소가 **서로 다른 거래처에 중복 등록**되면 경고하고 사람 확인을 요구한다. 자동으로 한쪽을 지우지 않는다 | `[MUST]` |
| FR-CPY-08 | **주소를 고치는 것은 허용하지 않는다.** 주소가 바뀌면 새 주소를 등록하고 옛 주소를 비활성화한다. 새 주소는 확인 상태를 **물려받지 않는다** | `[MUST]` |
| FR-CPY-09 | 사용자가 업무 관계를 승인·거부할 수 있다. 승인은 **주소 확인이 끝난 뒤에만** 가능하다 | `[MUST]` |
| FR-CPY-10 | 통신 상태를 활성·일시중지·비활성으로 바꿀 수 있다. 사유를 남긴다 | `[MUST]` |
| FR-CPY-11 | 각 주소의 현재 세 상태와 "왜 지금 보낼 수 없는가"를 화면에서 볼 수 있다 | `[MUST]` |
| FR-CPY-12 | 거래처·연락처·주소의 모든 생성·변경·상태 전이는 **감사 기록**에 남는다 | `[MUST]` |

### 4.3 개인 연락처 vs 공용 업무 메일함 `[OPEN]`

현실에는 두 가지가 있다.

| | 개인 | 공용 업무 메일함 |
| --- | --- | --- |
| 예 | `kim@k-transport.com` | `dispatch@k-transport.com` |
| 누가 답하나 | 그 사람 | 그때 담당인 누군가 |
| 담당자가 바뀌면 | 주소도 바뀐다 | **주소는 그대로** |
| 퇴사하면 | 비활성 | 영향 없음 |
| 확인의 뜻 | 그 사람이 응답 | **그 시점에 그 함을 여는 누군가**가 응답 |

**요구사항 차이가 실제로 있는가 — 분석 결과**

| 항목 | 차이가 있나 |
| --- | --- |
| 주소 확인 절차 | **없다.** 둘 다 "그 주소를 여는 사람이 응답했다"로 같다 |
| 발송 자격 판정 | **없다.** 세 상태 AND는 동일하다 |
| 회신 발신자 처리 | **있다.** 공용함에 보냈는데 개인 주소로 답이 오는 일이 흔하다(FR-INB-07) |
| 담당자 퇴사 처리 | **있다.** 개인은 비활성, 공용함은 그대로 |
| 표시 이름 | **있다.** 공용함에는 사람 이름이 없다 |
| 사건 기록의 역할·권한 | **없다.** 권한은 거래처의 역할에서 나오지 개인에게서 나오지 않는다 |

→ **차이는 있지만 첫 구현을 막을 만큼은 아니다.** 첫 구현에서는 구분 없이 "담당 연락처"로 다루고, 표시 이름에 팀 이름을 넣을 수 있게 한다. 구분 도입 여부는 `Q-48`. **이번에 구현 형태(`PERSON`/`ROLE_MAILBOX` 같은 구분값)를 확정하지 않는다.**

## 5. 이메일 주소 확인 (FR-EVF)

### 5.1 확인의 의미 — 넘지 말 것

> **"이 주소를 통제하는 사람이 CERA의 확인 요청에 응답했다."**

이것뿐이다. 법인 대표권·계약 체결 권한·회사 전체 권한을 뜻하지 않는다. 화면 문구·문서·코드 주석에 그 이상으로 쓰지 않는다.

## 9. 실제 발송 (FR-SND)

**특정 외부 API의 호출 방법을 정하지 않는다.** 시스템이 지켜야 할 행동만 적는다.

## 13. 사건 기록과 현재 상태 반영 (FR-EVL)

### 13.1 무엇이 사건으로 남는가

**모든 화면 클릭이 업무 사건이 되지 않는다.** 구분 기준은 *"현실의 업무 사실에 대한 주장인가"*다.

| 일어난 일 | 업무 사건 기록 | 감사 기록 |
| --- | --- | --- |
| 거래처·연락처 등록·변경 | ✕ | ● |
| 이메일 주소 확인 완료 | ✕ | ● |
| 업무 관계 승인 | ✕ | ● |
| 문의 초안 생성·수정 | ✕ | ● |
| **발송 승인** | ✕ | ● |
| 실제 발송(발송 행위) | ✕ | ● |
| 발송 실패·재시도의 **기술 원인** | ✕ | ✕ — 발송 시도 결과와 시스템 오류 기록(`system_error`)에 남는다(`23` 4.1) |
| 회신 수신 | ✕ | ● |
| 값 해석 실행 | ✕ | ● |
| **회신에서 나온 운영값**(트럭 가용, 야드 용량, 요율) | **●** | ● |
| **사람의 사실 확인·수정·거절** | **●** | ● |

> 발송 승인이 업무 사건이 아닌 이유: 현실에 대한 주장이 아니라 **CERA 안에서 내린 결정**이기 때문이다. 계획 승인과 같은 논리다(`05` 4.1).

| ID | 요구사항 | 우선 |
| --- | --- | --- |
| FR-EVL-01 | 검증을 통과한 회신 값만 업무 사건으로 기록한다 | `[MUST]` |
| FR-EVL-02 | 사건에는 **누가 말했는지(거래처·역할)·언제 말했는지·어디서 왔는지·원문 참조**가 붙는다. 이 값들은 **서버가** 정한다 | `[MUST]` |
| FR-EVL-03 | **기존 사건·상태 설계(`05`)를 바꾸지 않는다.** 외부 통신은 그 설계에 입력을 넣을 뿐이다. 새 상태 판단 규칙을 만들지 않는다 | `[MUST]` |
| FR-EVL-04 | 같은 원문을 두 번 처리해도 사건은 하나다 | `[MUST]` |
| FR-EVL-05 | 첫 구현이 다루는 사실은 **이번 문의가 실제로 묻는 것만**이다: 트럭 시간대별 가용 대수, 야드 규격별 용량, 최대 보관일, 보관 요율, 창고 일자별 수용량 | `[MUST]` |
| FR-EVL-06 | **컨테이너 자체의 사실**(통관·반출 등)은 회신에서 추출하지 않는다. 회신에 섞여 있으면 별도 보관하고 사람 확인으로 넘긴다 | `[MUST]` |
| FR-EVL-07 | 회신에서 나온 값은 **확정 사실이 되지 않는다.** 대개 "잠정"으로 반영되고, 사람 확인 요청이 함께 생긴다 | `[MUST]` |
| FR-EVL-08 | 기존 자원 값을 크게 **줄이는** 회신은 확인 전까지 반영을 보류하고, 기존 값을 유지한 채 높은 우선순위로 사람에게 알린다 | `[MUST]` |
| FR-EVL-09 | 이미 지난 시간대에 대한 제안은 판단에 쓰지 않는다 | `[MUST]` |
| FR-EVL-10 | 상태 반영 결과(무엇이 바뀌었나·왜·근거는 무엇인가)를 화면에서 되짚을 수 있다 | `[MUST]` |

## 23. 구현 기술을 지금 정하지 않는 이유

이 문서의 요구사항은 **아래 어느 것에도 묶여 있지 않다.**

| 아직 정하지 않는 것 |
| --- |
| AI 모델 이름·공급자·버전·SDK |
| 외부 메일 채널의 구체 호출 방법과 순서 |
| 인증 처리 라이브러리 |
| 데이터베이스 종류·접근 라이브러리 |
| 작업 처리·대기열 라이브러리 |
| 최적화 방식과 그 도구 |
| 데스크톱 앱 기술 |
| 배포 환경·컨테이너 구성 |

**왜 미루나**

1. 이 문서가 정의한 것은 **행동과 계약**이다. 같은 행동을 여러 기술로 만들 수 있고, 어느 것이 나은지는 **만들기 직전의 상황**(품질·비용·보안·성능·유지보수·그때의 기술 현황)에 달려 있다.
2. 지금 고정하면 **바꿀 이유가 생겨도 문서가 발목을 잡는다.** 특히 AI 모델은 몇 달 단위로 바뀐다.
3. 책임 경계(`18` O절)와 이 요구사항은 유지되어야 하지만, **구현 도구는 교체 가능해야 한다.** NFR-30이 이것을 시험으로 확인한다.

**단, 아래는 이미 정해졌고 바꿀 수 없다**: 책임 경계(무엇을 AI가 하고 무엇을 서버가 하는가), 사람 승인 게이트, 발송 자격 규칙, 사건·상태 설계(`05`), 원문 보존, 중복 발송 금지.

## 24. Implementation Planner Handoff

다음 단계에서 구현 계획을 세우는 사람이 **이 절만 읽어도 시작할 수 있어야 한다.**

### 24.1 이번 기능의 목표

Mock으로만 존재하던 외부 연락 루프를 **실제로 한 바퀴 돌린다**: 문의 초안 → 사람 승인 → 실제 발송 → 실제 회신 → 구조화 → 운영 사실 후보 → 화면 반영.
성공 판정은 "메일이 갔다"가 아니라 **"승인 없이는 안 나가고, 두 번 안 나가고, 회신 한 통으로 사실이 확정되지 않는다"**를 시험으로 증명하는 것이다.

### 24.2 확정된 것

- 요구사항: 이 문서 4~19절 (`FR-CPY` · `FR-EVF` · `FR-ELG` · `FR-COM-04~` · `FR-APV` · `FR-SND` · `FR-INB` · `FR-XAI` · `FR-STC` · `FR-EVL` · `FR-UI-09~` · `FR-AUD-02~` · `NFR-12~30`)
- 책임 경계: `18` O절 표
- 설계 결정: ADR-026·027·028·029 (모두 Accepted)
- 실제 발송 허용 조건: `01` 6.1절
- 사용자에게 보이는 상태 이름: 이 문서 15절
