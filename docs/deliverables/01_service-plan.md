## 1. 프로젝트 개요

**CERA(Container Exception Recovery Agent)** 는 수입 컨테이너 물류에서 **예외 상황이 생겼을 때**(예: 창고가 받을 수 있는 컨테이너 수가 갑자기 줄었을 때), 필요한 정보를 모으고 거래처에 묻고 답을 검증 가능한 사실로 바꾼 뒤, 비용과 운영 제약을 계산해 **복구 계획**을 제안하고, 사람 승인 뒤 후속 요청까지 이어 주는 **사람 승인 중심(Human-in-the-loop) 복구 의사결정 시스템**이다.

핵심 질문은 "컨테이너가 어디 있는가?"가 아니라 **"지금 무엇을 믿을 수 있고, 무엇을 해야 총손실이 가장 작은가?"** 이다.

## 2. 추진 배경

- 수입 컨테이너 운영의 사실은 공공 API(선박 입항 · 적하목록), 메일, 계약 요율, 현장 담당자에게 흩어져 있다.
- 계획이 틀어지는 순간(창고 수용량 감소, 트럭 부족 등) 담당자는 운송사 · ODCY(부두 밖 컨테이너 야적장) · 창고에 일일이 연락하고, 답을 모아 손으로 재배치를 계산한다.
- 상황이 또 바뀌면 처음부터 다시 계산하고, 이미 보낸 요청을 정정 · 취소해야 하는데 이 흐름이 기록으로 남지 않는다.

## 3. 문제 정의 (현재 구현이 다루는 범위)

| 문제 | 현재 구현에서 다루는 방식 |
| --- | --- |
| 창고 수용량 감소로 배정한 컨테이너가 넘침 | 시설별 일 수용량 사실(`capacity.day(D)`)을 놓고 대체 창고 · ODCY · 터미널 대기로 재배정 |
| 운송 자원(협력 트럭) 가용 여부를 모름 | 트럭 풀의 시간대별 가용 대수(`available.slot(...)`)를 정보 공백으로 판정하고 운송사에 문의 |
| ODCY 를 대안으로 쓸 수 있는지 모름 | ODCY 크기 유형 · 일 수용량을 문의 · 입력으로 확보 |
| 반출 기한 · 비용 위험(D&D · 보관료 · 운송비) | 계약 요율로 컨테이너 × 선택지 비용을 원 단위로 계산, 지연 · 대기 위험은 정책 벌점으로 |
| 거래처 확인 필요 | 등록 · 확인 · 승인된 주소에만 보내고(Contact Gate), 담당자가 없거나 여럿이면 사람에게 넘김 |
| 계획 변경 | 사실 · 입력이 바뀌면 이전 판을 `OUTDATED` 로 두고 재계산, 보낸 요청은 정정 · 취소 초안으로 |

다루지 않는 예외 유형(통관 지연, 선박 지연 자동 감지, 장비 고장 등)은 현재 구현에 없다. 예외 발생 자체를 **자동 탐지하는 기능은 없다** — 복구 실행은 시나리오 시드나 운영자가 만든다.

## 4. 기존 업무의 문제점

1. 정보 출처가 여러 곳이고, 어떤 값이 언제 · 누구에게서 왔는지 남지 않는다.
2. 메일 답장의 값을 사람이 다시 옮겨 적는다(오기 · 누락).
3. 비용 비교가 경험에 의존하고, 대안끼리의 총손실을 같은 기준으로 비교하기 어렵다.
4. 계획이 바뀌어도 이미 보낸 요청과의 차이를 추적하지 못한다.
5. 누가 어떤 판단으로 승인했는지 감사 기록이 남지 않는다.

## 5. 해결 방향

| 원칙 | 구현 |
| --- | --- |
| 모든 입력은 출처 · 신뢰 근거를 가진 사건으로 쌓고, 현재 값은 결정론 규칙으로 정한다 | `event` → Reconciliation → `canonical_fact` |
| AI 는 비정형 글(메일 답장)을 읽는 데만 쓰고, 출력은 후보일 뿐이다 | AI Server 추출 → Backend 결정론 검증 → 후보 |
| 숫자(비용 · 배정)는 결정론 엔진에서만 | Cost / Risk Engine · HiGHS Solver |
| 외부로 나가는 연락은 사람 승인 뒤에만 | 승인(`message_approval`) + 사람의 발송 요청 + Contact Gate |
| 바뀐 것은 덮어쓰지 않고 새 기록으로 | append-only 표 · 계획 판(version) · 정정 · 취소 초안 |

## 6. CERA 의 역할

CERA 는 WMS(창고 관리) · TMS(운송 관리) · FMS · ERP 를 **대체하지 않는다**. 이들이 가진 운영 데이터를 입력으로 받아, **예외가 났을 때의 판단과 후속 행동을 연결하는 층**(System of Action / Exception Recovery Layer — 실행 연결 계층, 예외 복구 계층)이다.

- 기록 시스템(System of Record)이 아니다 — 컨테이너 마스터 · 재고 · 배차의 정본은 기존 시스템이다.
- 현재는 기존 시스템과 **직접 연동하지 않는다**. 운영 데이터는 CSV · 행(JSON) 입력과 사람 입력으로 받는다. 고객 시스템 Connector 는 [향후][외부 의존] (QUEUE T-126).

## 7. 주요 사용자

권한 정본: `back/src/auth/permissions.ts`. 화면은 버튼을 숨길 뿐이고 막는 것은 Backend Guard 다.

| 데모 방문자 `DEMO_VISITOR` | 공개 포트폴리오 체험 | 전부(읽기, 합성 데이터) | 운영자에서 운영 입력 · 공공데이터를 뺀 것 | 등록부 · 사용자 관리 · 운영 입력 · 공공데이터 · 실제 채널 발송 |

사람이 아닌 행위자: **AI Agent**(LangGraph — 서비스 토큰으로 Tool 만 호출, 승인 권한 없음) · **Worker**(SYSTEM — 발송 · 수신 · 추출 · 재조정) · **외부 거래처**(메일로 답장).

## 8. 핵심 업무 흐름

```text
복구 실행(시나리오 시드 · 운영자가 만든 실제 실행)
 → Agent 시작 → 정보 공백 판정(결정론)
 → 담당 거래처 · 주소 찾기(Contact Gate) ── 없거나 여럿이면 사람이 등록 · 선택
 → 문의 초안(구조화 값 + 숫자 검사) → 사람 승인 → 사람의 발송 요청 → Worker 발송(Mock 또는 Gmail)
 → 답장 수신(원문 보존 · 발신자 판정) → AI 추출 → 결정론 검증 → 후보 → 임시 사실
 → (사람 확인 · 정정 · 직접 입력)
 → 비용 · 위험 계산 → Solver → 복구 계획 판 → 사람 승인
 → 후속 요청 초안 → 사람 승인 · 발송
 → 사실 · 입력 변경 → 계획 OUTDATED → 재계산 → 새 판 승인
 → 이미 보낸 요청과 다르면 정정 · 취소 초안 → 사람 승인 · 발송
```

## 10. 서비스 가치

- 값마다 출처 · 근거(원문 인용) · 시각이 남아 "왜 이 값을 믿는가"에 답할 수 있다.
- AI 가 틀려도 값이 그대로 반영되지 않는다(검증 탈락 → 사람 검토).
- 대안들의 총손실을 같은 기준(원 단위 비용 + 위험 벌점)으로 비교하고 기준안 대비 절감액을 보인다.
- 계획 변경 시 무엇이 왜 바뀌었는지(판 비교 · OUTDATED 이유)와 이미 보낸 요청의 정정 · 취소가 이어진다.
- 승인 · 발송 · 사실 판단 모두 감사 기록이 남는다.

| 메일(Gmail) | 실제 연동 구현 · 검증(OAuth, CERA 전용 계정 하나) |
| 배차 · 예약 시스템 Write | 하지 않음(계획 승인 ≠ 실행) |

- 사람 승인이 필요한 모든 외부 행동
