## 1. 목적

DB 개념 설계에 들어가기 직전에, 저장소 문서를 기준으로 다음을 가른다.

1. 이미 확정되어 **DB가 반드시 따라야 하는 규칙**
2. 설계는 충분하지만 **아직 사람 승인 전인 제안**
3. 문서·시나리오·코드 사이에서 **서로 어긋나는 부분**
4. 개념 설계 **전에 반드시 사람이 결정해야 하는 문제**
5. **구현 중 또는 미래로 미뤄도 되는 문제**

### 1.1 이번 검토가 하지 않은 것

- Table / Column / PK / FK / SQL / Migration 설계
- 기술 선택 (DB 제품, ORM, 백엔드 언어, LLM 공급자·모델, 솔버, 클라우드, 큐)
- 저장소에 없는 내용을 일반적인 물류 상식으로 채우기 — **외부 도메인 확장은 개념 설계 단계에서 별도로 한다**
- 기존 문서의 대규모 수정 (6절에 "동기화 필요" 목록만 만든다)

## 5. Scenario Assumption (C그룹) — 제품 규칙이 아니다

`data/scenarios/busan-wh-capacity-01/`과 그 README에만 있는 값이다. **DB 제약으로 올리면 안 된다.**

| 가정 | 값 | 출처 |
| --- | --- | --- |
| 컨테이너 수 | 30대 | validator가 `=== 30` 강제 |
| 창고 A 수용량 | 하루 20 → 11:00에 8 | 시나리오 |
| 영향 컨테이너 | 12대 | 시나리오 |
| 자사 트럭 | 8대, 트럭별 근무 시간 상이 | `resources.json` |
| 협력사 트럭 | K운송 2대, 회신 이후에만 | 시나리오 |
| ODCY 용량 | A 40FT Dry 5 → 4, B Dry 6(Reefer 불가) | 시나리오 |
| 최대 보관일 | ODCY A 2일 | 회신값 |
| 창고 당일 입고 마감 | 16:00 | `last_departure_for_same_day` |
| ODCY B 왕복 | 2시간(2슬롯 점유) | `resources.json` 주석 `[ASSUMPTION]` |
| 배차 슬롯 | 1시간 단위, 13~19시 | 시나리오 |
| **입고일은 계획이 바꾸지 못한다** | 규칙 | `plans.cost_scope.delivery_day_rule` + validator 강제 |
| 입고일 배분 | 10/14 6대, 10/15 6대 | **README 산문에만 존재** |
| 모든 요율 | `[ASSUMPTION]` 자리표시 | validator가 태그 강제 |
| 금액 | Baseline 4,650,000 / v1 3,835,000 / v2 3,855,000 | 시나리오 명시값 |

> **"입고일은 계획이 바꾸지 못한다"가 특히 주의 대상이다.** validator가 강제하지만 정본 문서 어디에도 제품 규칙으로 적혀 있지 않다. 시나리오 단순화인지 제품 규칙인지 **확인이 필요하다**(18절 Q-D3).

## 7. 원본 vs 파생 vs 계산 결과

이전 조사에서 "테이블로 만들면 안 된다"고 표현한 것을 **더 정확히** 나눈다.

### 7.1 A — 원본 진실 데이터 (source of truth)

**절대 재생성할 수 없다. 잃으면 끝이다.**

| 대상 | 근거 |
| --- | --- |
| 원문 보관소(수신한 메일·API 응답·업로드 파일 원본) | `01` 5.7, `05` 13절 |
| 사건 기록(Event) | `05` 13절 "INSERT만" |
| 사람의 결정 기록(계획 승인·발송 승인) | `05` 11.5, ADR-028 |
| 감사 기록 | `07` 4절 append-only |
| 등록 정보(컨테이너·자원·거래처·연락처·계약 마스터) | `07` 4절 |

### 7.2 B — 파생값, 그러나 **저장(물질화)한다**

**언제든 지우고 사건에서 다시 만들 수 있어야 한다.** 저장하는 이유는 성능·변경 감지·설명이다.

| 대상 | 저장 여부 | 근거 |
| --- | --- | --- |
| 현재 상태(Canonical Fact) | **저장함** | `05` 9.4 "파생 테이블", 13절 "언제든 지우고 재생성" |
| └ 그 안의 `freshness_status` | **저장함**(파생 테이블 컬럼) | `07` 4절. 단 **사건에는 저장하지 않는다**(`05` 4.2) |
| └ 그 안의 `decision_usability` | **저장함** | 같음 |
| 충돌 | 저장함 | `07` 4절 "파생" |
| 확인 요청 | **저장함 — 단 순수 파생이 아니다** | `05` 11.2 "요청 목록은 파생. **사용자 처리 이력(열람·미룸)만 따로 저장**" |

> **⚠ 확인 요청이 예외다.** 목록은 파생이지만 사람의 처리 이력은 파생이 아니다. **파생 테이블을 지우면 처리 이력이 사라진다.** 개념 설계에서 이 둘을 분리해야 한다(18절 Q-C2).

**이전 보고 정정**: 제가 "`freshness_status`는 테이블로 만들면 안 된다"고 했는데 부정확했다. 정확히는 **사건(Event)에 저장하면 안 되고**, 파생 테이블에는 물질화되어 있다.

### 7.3 C — 독립적인 계산 결과 기록 (저장해야 한다)

**재현·감사·비교를 위해 남긴다. 파생이지만 "그때 그 입력으로 그렇게 계산했다"는 기록 자체가 가치다.**

| 대상 | 왜 저장하나 |
| --- | --- |
| 계획 입력 스냅샷 | 계획 재현(`snapshot_hash`), 승인 시 입력 불변 확인 |
| 위험 평가 결과 | 시점별 비교, 등급 근거 |
| 복구 계획 실행·배정 | 입력 해시·규칙 버전·시드와 함께 저장해 재현 |
| 비용 내역 줄 | 12절 참조 — **저장 구조가 아직 없다** |

### 7.4 D — 지금은 저장하지 않는 조회 시 조립값 (**성능상 캐시는 열려 있다**)

| 대상 | 현재 | 캐시 가능성 |
| --- | --- | --- |
| 컨테이너 단계(`phase`) | 조회 시 유도(`04` 2.2, `13`) | **가능**. 단 **진실의 원천이 되어서는 안 된다** |
| 자원 영향(`impacts`) | Risk가 계산, 저장 안 함(`04` 2.3) | 가능 |
| 엔티티 뷰 조립값(`ready_at`, `worst_usability`, `last_evidence_at`) | 조회 시 조립(`05` 9.2) | 가능 |
| 사건 수준 확인 상태·대체 상태 | `as_of`마다 계산(`05` 6.1) | 가능 |

> **"절대 저장 금지"가 아니라 "진실의 원천으로 삼지 말 것"이다.** 나중에 성능 때문에 캐시하는 것은 이 원칙을 깨지 않는다. 조건은 두 가지다: ① 사건에서 다시 만들 수 있을 것 ② 캐시가 원본과 다르면 원본이 이길 것.

### 10.3 판정

| 질문 | 판정 |
| --- | --- |

## 11. 운송사 / 차량 / 가용량

### 11.1 네 가지를 혼동하지 않는다

| 개념 | 현재 표현 | 성격 |
| --- | --- | --- |

| 차량 풀 | `TRUCK_POOL` 엔티티 유형 | 마스터 |

| 특정 시간의 가용 대수 | `available.slot(S)` — **제안(OFFER) 종류의 사실** | **사실** |

### 11.2 분석

> **⚠ 2026-09-16 결론 수정.** 이 문서 초안은 "개별 차량 엔티티가 필요하다"고 결론 냈다. **그 결론을 철회한다.** 검증 스크립트가 차량별 근무시간과 중복 배차를 검사한다는 사실만으로 CERA MVP의 제품 요구사항이 되지 않는다. 시나리오의 `TRUCK-01`~`08`은 **시나리오 구현상의 상세 표현일 수 있다.**

| 질문 | 근거 | **판정 (2026-09-16)** |
| --- | --- | --- |
| MVP가 개별 차량 엔티티를 실제로 필요로 하나 | 검증기가 차량별 근무시간·중복 배차를 검사하고 배차가 차량 id를 쓴다. **그러나 그것은 시나리오 재현의 요구이지 제품의 요구라는 근거가 아니다** | **확정하지 않는다.** MVP는 **운송사 + 차량 풀 + 시간별 가용량**만으로 충분할 가능성이 있다 → **Q-57** |
| 개별 차량을 어떻게 다루나 | — | **개념 후보로 유지.** 실제 배차 수준의 관리가 필요해질 때 도입한다 |
| 자사만 개별 관리하고 외부는 제안만 관리해도 되나 | 데이터가 이미 그렇게 한다(K운송 `trucks: []`). 그런데 배차는 `K-TRUCK-1`이라는 id를 쓴다 | **개념 모델에서 검토** (개별 차량 도입 여부에 딸린 문제) |
| "15시에 3대 가능"은 차량 마스터인가 제안인가 | `05` 4.3이 **제안(OFFER)** 으로 명확히 분류 | **유지 — 제안이다** |
| 기사(Driver) 엔티티가 필요한가 | 저장소에 **없다** | **범위 밖** |
| 배차 슬롯은 현실인가 계획인가 | 계획 안에 있다(`plans.json`). 실제 배차 결과는 저장소에 없다 | **계획의 일부. 실제 결과는 미래** |

**개념적으로 네 가지는 분명히 구분한다** (이것은 확정):

```text
운송사(조직)      = 거래처의 한 종류
차량 풀           = 운송사가 가진 차량 자원의 집합
가용 제안·관측     = "15시에 3대 가능" — 사실(OFFER)이지 마스터가 아니다
개별 차량         = 실제 차량 한 대 — MVP 필수 여부 미확정
```

## 13. 현실 / 관측 / 계획 / 실제 결과

### 13.1 분리는 잘 돼 있다

`05` 2.1의 사실 종류가 이미 축을 나눠 놓았다.

| 종류 | 뜻 | 예 |
| --- | --- | --- |
| 마일스톤·상태 | **관측한 현실** | 반출 시각, 통관 상태, 위치 |
| 제안(OFFER) | 상대가 약속한 미래 가용 | "15시 2대 가능" |
| 예정(PLAN) | **CERA 사용자의** 의도 | 픽업 예정 시각, 입고 예정일 |
| 예상(FORECAST) | 외부·CERA의 추정 | 도착 예상 시각 |

- **예정·예상이 관측을 덮어쓰는 일이 구조적으로 불가능하다** — 서로 다른 키이기 때문이다(`05` 2.1).
- 도착 예상과 실제 도착은 별도 키이고, 실제가 생기면 예상은 판단에서 빠진다(R7-f).

### 13.2 그러나 "계획"이 두 곳에 있다

| 무엇 | 어디 | 성격 |
| --- | --- | --- |
| `plan.pickup_at`, `plan.destination_day` | 컨테이너의 **사실** | 사용자가 입력한 예정 |
| 복구 계획 실행·배정 | **엔진 산출물** | 최적화 결과 |

**둘은 다른 것인데 둘 다 "계획"이라 불린다.** 개념 설계에서 이름을 갈라야 한다(Q-A5).

### 13.3 실제 결과(Actual Outcome)는 별도 개념이 아니다

`06` 7절 G5가 "실행 결과(Pilot) → 마일스톤 Event"라고 정했다. 즉 **실제 결과는 별도 엔티티가 아니라 관측 사실로 들어온다.** 일관된 설계다.

다만 **"계획대로 실행됐는가"를 비교하는 구조는 없다.** 실현 절감 측정이 Pilot이므로 지금은 문제가 아니다. → **미래**

| **현재 시나리오에서 Recovery Plan이 입고일을 바꾸지 않는다** | **정본 문서에 제품 규칙으로 없다.** 데이터와 검증기에만 존재한다. **CERA 전체 제품 불변식으로 승격하지 않는다** (2026-09-16 결정) |
| `K-` 접두로 협력사 차량 판별 | fixture 명명 규칙 |

### 16.E 화면 / fixture / 문서 품질 검사

KPI 값이 위험 상태와 일치 · 등급별 개수 합 · 노출액 합 · 12대/20대 개수 항등 · 계획 합계 · 이전 계획 숫자 일치 · 모든 파일의 시뮬레이션 표시 · **금지 발표 문구 검사** — fixture가 스스로 모순되지 않는지와 발표 품질을 보는 검사다. 제품 제약이 아니다.

## 22. Conceptual Data Model Planner Handoff

### 22.1 이 단계의 목표

**테이블이 아니라 개념과 관계를 정한다.** 어떤 것이 독립 엔티티이고, 무엇이 무엇에 속하며, 어떤 것이 사실이고 어떤 것이 산출물인지.

### 22.2 반드시 지켜야 할 것

3절의 A-01 ~ A-24 (24개 확정 규칙). 특히:

- 사건은 덧붙이기만, 출처 필수, 시간대 필수, 원 단위 정수, 원문 보존
- 현재 상태는 사건에서 재생성 가능해야 한다
- 사실과 산출물을 섞지 않는다
- 예정·예상·관측·제안은 서로 다른 사실이다
- 사실 확인 · 계획 승인 · 발송 승인은 서로를 대신하지 않는다
- AI는 상태·신원·권한·강도를 정하지 않는다
- 거래처 → 연락처 → 채널 주소, 세 상태 분리

### 22.3 전제로 삼을 것 — 2026-09-16 갱신

| **019·020·021** | **`Accepted (구조 한정)`** | **구조를 전제로 삼는다.** 정책 파라미터 값은 개념 모델의 관심사가 아니다 |
| 013 (덧붙이기 + 물질화) | Proposed — 단 `01` 5.4가 규칙으로 못박음 | 전제로 삼는다 |

### 22.6 분석해야 할 개념 목록

아래 개념을 하나씩 분류한다. **"JSON에 있으니 테이블"이라고 결론 내리지 않는다.**

```
Actor · Counterparty · Contact · Channel Address
Container · B/L
Facility · Warehouse · Terminal · ODCY
Carrier · Truck Pool · Availability(Offer)
Event · Canonical Fact · Conflict · Verification
Contract · Tariff · Rate Quote
Operational Plan · Recovery Plan · Planning Snapshot
Risk Result · Cost Result
Communication · Audit
```

각 개념을 다음 중 **무엇인지** 정한다.

| 분류 | 뜻 |
| --- | --- |
| **독립 엔티티** | 그 자체로 존재하고 식별된다 |
| **속성** | 다른 개념에 딸린 값이다 |
| **관측·사건** | 출처가 주장한 사실이다 |
| **파생 상태** | 사건에서 계산되는 현재 값이다 |
| **계획** | 의도이지 현실이 아니다 |
| **계산 결과** | 엔진 산출물이다 |
| **근거(Evidence)** | 왜 그렇게 판단했는지의 기록이다 |
| **뷰** | 조회 시 조립하는 것이다 |
| **보류** | 지금 정하지 않는다 |

**분류할 때 함께 적을 것**: 무엇으로 식별되는가 · 무엇과 관계가 있는가 · 원본인가 파생인가 · 시간 축이 필요한가(시점별로 값이 달라지는가) · MVP 필수인가.

### 22.7 개념 설계 단계에서도 하지 않을 것

**SQL을 쓰지 않는다.** 테이블·컬럼·키·자료형·인덱스를 확정하지 않는다. 기술 선택을 하지 않는다.

### 22.8 이미 답이 나온 것 (다시 묻지 말 것)

18절 표 참조. 상태 구조 · B/L 독립 · Facility 상위 개념 · 계획 용어 분리 · Actor 도입은 **결정됐다.**

### 22.9 개념 설계 중 마주칠 열린 질문

**Q-53**(B/L 개수 관계) · **Q-56**(Destination의 위치) · **Q-57**(개별 차량 MVP 필수 여부) · **Q-61**(활동 타임라인)은 개념 모델을 만들면서 답할 수 있다.
**Q-54·55·58·59·60·62·63**은 **논리 설계로 미뤄 둔 것**이므로 개념 단계에서 확정하지 않는다.

### 22.7 외부 도메인 확장

이번 검토는 **저장소 문서만** 근거로 삼았다. 일반적인 물류 도메인 지식으로 빈 곳을 채우지 않았다. 개념 설계 단계에서 외부 지식을 쓰려면 **어디까지가 저장소 근거이고 어디부터가 확장인지 구분해서** 표시해야 한다.
