# 시나리오 데이터 팩 — `busan-wh-capacity-01` (Prototype 판, v0.1.0)

- 작성: T-061 (2026-09-15). 소비자: `front/web/`의 MockProvider(`docs/16_frontend-prototype.md`)
- 모든 값은 합성(`is_simulated = true`)이다. 실제 화주·컨테이너·요율·항만 배치가 아니다.
- 결과값(위험·비용·계획)은 엔진 결과가 아니라 **시나리오에 명시한 결과(`SCENARIO_RESULT`)**다. Solver·Risk·Cost Engine은 아직 없다.
- 정합성 검사: `cd front/web && npm run validate:scenario`

## 3. 숫자 (시뮬레이션 기준, KRW)

| 항목 | 값 | 산식 |
| --- | --- | --- |
| Baseline (영향 12대, 조치 없음) | 4,650,000 | 12대 × (터미널 대기 Demurrage·보관료 + 직송 운임) |
| 정상 직송 운임 (12대) | 2,160,000 | 40FT 9 × 190,000 + 20FT 3 × 150,000 |
| Current Exposure | 2,490,000 | Baseline − 정상 직송 운임 |
| Plan v1 | 3,835,000 | ODCY A 5 · ODCY B 4 · 대기 3 |
| Plan v1 절감 | 815,000 | 4,650,000 − 3,835,000 |
| Plan v2 | 3,855,000 | ODCY A 4 · ODCY B 6 · 대기 2 |
| Plan v2 절감 | 795,000 | 4,650,000 − 3,855,000 |
| 직송 유지 8대 (비교 제외) | 1,600,000 | 세 계획 모두 같음 |

- 창고 A 입고일은 수용량이 정한다(이월 12대 → 10/14 6대, 10/15 6대). 세 계획에서 같다. 계획이 바꾸는 것은 입고일까지 컨테이너를 **어디에 둘지**다.
- v2가 v1보다 20,000원 비싸다. v1은 ODCY A 5대를 가정했지만 실제 4대라 1대가 실행 불가였고, 운송사 추가 트럭으로 C008을 옮겨 일부 만회했다. "회신이 계획의 가정을 바로잡는다"를 보여주는 장면이다.

## 4. `[PROPOSED]` 시나리오 fixture 수정 (09 예시값과 다른 점)

`09_mvp-scenario.md`의 예시값(Baseline 6,420,000 / Recovery 2,850,000 / Saving 3,570,000원, 배정 8/5/4/3)은 **복사하지 않았다.**

1. 예시 배정 8/5/4/3(합 20)은 "원래 창고 대상 20대 배치"로 해석해 v1에 그대로 살렸다. "영향 12대 Recovery Actions"는 5/4/3(합 12)으로 따로 둔다.
2. 금액은 비용 항목 단가(`resources.json` rates, `[ASSUMPTION]`)에서 아래에서 위로 합산해 정했다. 운송비까지 포함한 TotalCost라 예시값(운송비 포함 여부 불명)과 규모가 다르다. 예시 금액을 맞추려고 단가를 역산하지 않았다.
3. 회신 시각을 11:40·11:45·11:50에서 11:15·11:18·11:20으로 당겼다(데모 흐름, 2026-09-14 사람 지시).
4. D0를 2026-10-05(개천절 대체공휴일)에서 2026-10-13(화)으로 옮겼다.
5. Reefer 4대를 넣었다(09 6절은 Reefer를 범위 밖으로 뒀지만, 브리프가 Dry/Reefer 차이를 요구했다. Reefer 전용 자원은 모델링하지 않고 "ODCY 불가 → 직송"으로만 쓴다).

## 5. 수정 방법

값은 JSON에 직접 적혀 있다. 한 값을 바꾸면 관련 합계(비용 항목 → 조치 → 계획 → KPI)도 함께 고쳐야 하고, `npm run validate:scenario`가 어긋난 곳을 알려준다.
